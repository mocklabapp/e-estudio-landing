# Publish approved languages

e estudio enables Spanish at `/` and Catalan at `/ca/`. English registry/UI resources remain disabled and are not a complete approved English client site. Native Astro i18n and strict TypeScript own routing/publication without a translation dependency or language-switching JavaScript. Editorial pages are static; ES/CA homes and portfolios render on demand. See [the current route/content map](e-estudio-localization.md).

## Enable English only after approval

1. Confirm approved English copy, page coverage, UI and metadata. Current feature components are localized for ES/CA; extend their domain copy/rendering deliberately rather than assuming the generic English resources translate this client website.
2. In `src/i18n/locales.ts`, retain ES/CA and add English: `['es', 'ca', 'en']`.
3. Add or review each translation in `src/data/pages.ts`; omit pages whose English is not ready.
4. Set Astro's `site` to the actual production URL in `astro.config.mjs` before launch.
5. Run `pnpm run validate` on Node 24.x with pnpm 12.16.1, then inspect real language links and affected pages in a browser.

Disabling English again removes `/en/` output, selector links and English hreflang on the next build. Deploy fresh build output rather than retaining stale files from previous releases.

## Add another language independently

For French with English still disabled:

```ts
// src/i18n/locales.ts: add to locales, keeping existing entries.
fr: { label: 'Français', lang: 'fr', dir: 'ltr' },
// Change only the enabled list:
export const enabledLocales: readonly string[] = ['es', 'ca', 'fr'];

// src/i18n/ui.ts: add the approved UI dictionary.
fr: { navigation: 'Navigation des langues', languageSwitcher: 'Langue' },
```

Add approved `fr` translations to the selected pages. These snippets describe edits to existing objects, not complete standalone modules. Registry additions extend the `Locale` type; TypeScript requires the new UI dictionary. Generic page rendering needs no copied shell. This client's feature renderer currently selects ES/CA explicitly: extending the full client site also requires approved domain translations, feature rendering and any live route equivalents, with focused tests. Do not enable a locale expecting the generic registry to synthesize those pages.

For an RTL locale, register its actual HTML language tag and `dir: 'rtl'`. The layout emits that direction, but the base does **not** guarantee RTL typography, layout or accessibility. Agree fonts, design and target-browser checks for that client.

## Page coverage and translated slugs

Give each page entry a unique stable ID, with all its locale translations inside that one entry. For example, a client-approved page could have:

```ts
{
  id: 'about',
  translations: {
    es: { slug: 'acerca', title: 'Acerca', description: 'Descripción aprobada.', body: 'Texto aprobado.' },
    en: { slug: 'about', title: 'About', description: 'Approved description.', body: 'Approved copy.' },
  },
}
```

This generates `/acerca/` and, only when English is enabled, `/en/about/`. Slugs are relative without leading/trailing slashes; use `''` for the home page. Keep IDs and resulting routes unique. This is an example, not production business content.

- Page-entry IDs must be unique by exact string equality, even when their slugs differ. A duplicate fails before translation publication with `[i18n] Duplicate page ID <id>.` Multiple locale translations inside one page entry share its single ID and are valid.
- Published output paths must be unique across all enabled locales. A Spanish slug such as `en` collides with the enabled English home. Builds reject this before static generation with `[i18n] Colliding published path /en/: <id>/es and <id>/en.` (record order follows content order), rather than silently dropping either page.
- Every page must have complete Spanish content. Keep the Spanish home at the empty slug.
- Optional page translations can be absent. Omit the locale key, not its fields; never use empty strings as placeholders.
- Provided published translations require a slug (empty is valid for home), title, description and body. Enabled UI must contain both labels. Invalid publication fails with an intentional `[i18n]` diagnostic.
- Missing optional translations generate no route, alternate or selector link. A missing translation never links to that language's home or substitutes Spanish.
- All public text, including UI and metadata, needs approved translations. Shared identity remains in `site.name`; do not duplicate the site's configuration per language.

The client navbar uses ES/CA links; the shared selector supports locale labels with `lang`, `hreflang` and `aria-current`. It hides when the current page has no alternative. URLs are explicit: no language-detection redirects, automatic runtime translation or fallback configuration.

## Local copy and live projects use the same language

Language links are native anchors: selecting an available equivalent loads its full page, including local copy and UI. Local content is currently typed TypeScript in `src/data/pages.ts`, not JSON. There is no SPA navigation or stored language preference.

Current client homes, cards and details call `selectPilotProjectContent(project, locale)`: a complete selected translation or the whole original, never mixed fields. Missing localized pages return 404; unknown original language is not inferred. This approved project-text policy is separate from page publication's no-fallback rule.

The [copyable SSR composition](projects.md#consume-in-native-astro-frontmatter) demonstrates the retained shared exact-language helper `selectProjectContent`, not the client's whole-original presentation policy. It looks up one page locale for local copy/UI and project text, leaving missing/partial content explicit. Each request fetches fresh data; open tabs do not poll.

To add a language, register its metadata, supply approved UI and local page translations, enable it, then build/validate. The pure selector accepts exact language keys without `es`/`en` branches, but database data-language validation remains independent and unchanged. Neither project translations nor selector calls enable page locales or synthesize copy. Local-only pages remain static.

## SEO and deployment

`BaseLayout` renders per-page `lang`, `dir`, title and description while retaining optional title/description props for existing consumers. On published localized pages it emits a self canonical and reciprocal hreflang only for enabled, available equivalents; Spanish also supplies `x-default`.

Absolute SEO links require Astro's configured `site`. Without a known production domain, this site intentionally omits canonical/alternate head links; normal relative language links still work. Do not invent a domain, treat test `https://example.test` as client configuration or add a sitemap integration without a requirement.

## Verification and language changes

`pnpm run validate` checks strict types, normal output and Node tests. The four original identity/metadata/Tailwind checks remain. `tests/i18n.test.mjs` exercises public programmatic Astro builds with isolated config/content variants, a single copied dependency tree per suite, fresh scratch/cache directories and asserted success or intentional failure exits. It does not inspect private implementation helpers or Git history. Fixtures do not mutate the original configuration/content.

Before changing languages, record affected page coverage, content/UI/metadata readiness and approvers in [the project brief](project-brief.md), following [the change checklist](project-kickoff.md). Preserve approved ES/CA and the existing URL/page-publication policy. Do not restart client discovery. Browser, keyboard/focus, contrast, translated layout and any RTL design checks remain necessary; generated HTML tests are not visual verification.
